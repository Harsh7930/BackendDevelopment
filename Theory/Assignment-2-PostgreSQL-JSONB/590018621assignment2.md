# Assignment 2: PostgreSQL as SQL + NoSQL with JSONB

## Learning objective

Understand how PostgreSQL's `jsonb` type supports both relational and document-style data, and consider when it can be used instead of MongoDB.

## Part A: Conceptual questions

### 1. What is `jsonb`, and how does it differ from `json`?

PostgreSQL provides two JSON types. The `json` type stores the original JSON text, so it preserves such details as whitespace, key order, and repeated object keys. PostgreSQL checks that the text is valid JSON, but it must parse that text again when evaluating many operations. The `jsonb` type parses JSON on input and stores a decomposed binary representation. It does not preserve whitespace or key order, and if an object repeats a key, the last value is retained. This conversion adds work on writes, so inserting or updating `jsonb` can be somewhat slower than storing the same input as `json`. In exchange, queries generally avoid reparsing the document and can use indexes such as GIN, making repeated searches much faster. The difference matters most for data that is queried often; if exact input formatting must be preserved, `json` may be more appropriate. Both types support JSON operators, but index support is a practical advantage of `jsonb`.

```sql
CREATE TABLE event_log (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload JSONB NOT NULL
);

SELECT payload ->> 'event_type' AS event_type
FROM event_log
WHERE payload @> '{"event_type": "purchase"}';
```

### 2. How can PostgreSQL act as SQL and NoSQL in the same table?

PostgreSQL can keep fields that every product must have in ordinary typed columns, while placing product-specific or changing fields in one `jsonb` column. This is a hybrid design: relational columns provide constraints, predictable types, joins, and straightforward reporting, while the JSON document allows different rows to carry different optional attributes. For example, a book can have `author` and `pages`, whereas a laptop can have `ram_gb` and `cpu`, without adding a new table column for every possible attribute. The table still has a relational schema; JSONB does not make the database schemaless. The application should validate document shape and types where those details matter, and frequently queried attributes may deserve constraints, generated columns, or indexes. This design is useful when entities share a stable core but have a controlled amount of variation. It avoids a separate document database for many workloads, while retaining SQL transactions and relationships. Common fields also remain easy to validate.

```sql
CREATE TABLE products (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price NUMERIC(10, 2) NOT NULL CHECK (price >= 0),
    attributes JSONB NOT NULL DEFAULT '{}'::jsonb
);
```

### 3. What do `->`, `->>`, `@>`, and `?` do?

The `->` operator extracts a JSON value and keeps it as JSON/JSONB; `->>` extracts the value as SQL text. That distinction matters when displaying a value or converting it to a SQL type for comparison. Given `{"author":"A. Writer","pages":320}`, `attributes -> 'pages'` returns the JSON number `320`, while `attributes ->> 'pages'` returns the text value `320`. The containment operator `@>` checks whether the left JSONB value contains the right-hand JSON structure. The key-exists operator `?` checks whether a top-level object key (or top-level string in an array) exists. The following expressions illustrate their results for a book row with those attributes: the first two return `320` in different types, containment returns `true`, and key existence returns `true`. These operators can appear in `SELECT` expressions or filters. Use `->>` when a SQL text value is needed, and cast it explicitly before numeric comparisons; use `@>` for matching a JSON structure. For example, casting extracted `pages` to `integer` lets the query compare it numerically rather than alphabetically as text.

```sql
SELECT attributes -> 'pages' AS pages_json,
       attributes ->> 'pages' AS pages_text,
       attributes @> '{"author":"A. Writer"}' AS has_author,
       attributes ? 'author' AS author_key_exists
FROM products
WHERE name = 'Designing Data';
```

Expected values: `pages_json` is `320` (JSONB), `pages_text` is `320` (text), `has_author` is `true`, and `author_key_exists` is `true`.

### 4. How can a GIN index change JSONB query performance?

A GIN index stores searchable components of JSONB documents, allowing PostgreSQL to find candidate rows without reading every document. The default `jsonb_ops` GIN operator class supports containment (`@>`), key existence (`?`), and related existence operators. This can help when a large table is frequently searched for documents containing a particular key/value structure. For example, a query for products whose attributes include `{"wireless": true}` can use a GIN index on `attributes`. A plain GIN index does not automatically speed up every JSON expression: a range condition such as `(attributes ->> 'ram_gb')::int >= 16` extracts and casts a value, and that expression does not match the standard GIN index's supported search form. A dedicated expression index may suit that query better. Indexes also require storage and add work to inserts and updates. Finally, on a tiny table the planner may correctly choose a sequential scan even when a GIN index exists, so an index definition alone is not evidence of a faster execution. Compare actual plans on representative data.

```sql
CREATE INDEX idx_products_attributes
    ON products USING GIN (attributes);

EXPLAIN ANALYZE
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

### 5. When could PostgreSQL JSONB replace MongoDB, and when might MongoDB fit better?

PostgreSQL with JSONB can replace a MongoDB deployment when the application needs flexible document attributes but also benefits from relational transactions, joins, foreign keys, and SQL reporting. It is especially compelling when the team already operates PostgreSQL and documents have a stable relational core. Typed columns and constraints can enforce important parts of the schema, while JSONB holds less predictable fields; however, PostgreSQL will not automatically validate every document against an application-specific schema unless constraints or application validation are added. MongoDB can be a better fit when the product is document-centric, most reads and writes operate on whole documents, and the team values its document query model and built-in sharding capabilities for horizontal distribution. PostgreSQL supports replicas and can be scaled or sharded with additional architecture or extensions, but that is not identical to turning on a GIN index. Both systems support transactions, though PostgreSQL is a natural choice for workflows spanning related rows and joins. The decision should follow consistency, query, operational, and scaling needs rather than the label SQL or NoSQL.

```sql
-- Relational constraints and document attributes can coexist.
CREATE TABLE inventory (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku TEXT UNIQUE NOT NULL,
    details JSONB NOT NULL DEFAULT '{}'::jsonb
);
```

## Part B: Hands-on exercise: Product catalog

The examples below use three categories. Books have `author` and `pages`, laptops have `ram_gb` and `cpu`, and accessories have `color` and `wireless`.

### Task 1: Schema

Run this in a fresh database or schema where `products` does not already exist.

```sql
CREATE TABLE products (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    category VARCHAR(50) NOT NULL,
    price NUMERIC(10,2) NOT NULL,
    attributes JSONB
);
```

### Task 2: Insert five products

```sql
INSERT INTO products (name, category, price, attributes) VALUES
    ('Clean Code', 'book', 499.00,
     '{"author":"Robert C. Martin","pages":464}'),
    ('Designing Data-Intensive Applications', 'book', 699.00,
     '{"author":"Martin Kleppmann","pages":616}'),
    ('ThinkPad T14', 'laptop', 1299.00,
     '{"ram_gb":32,"cpu":"AMD Ryzen 7"}'),
    ('MacBook Air', 'laptop', 1099.00,
     '{"ram_gb":16,"cpu":"Apple M-series"}'),
    ('Wireless Mouse', 'accessory', 29.99,
     '{"color":"black","wireless":true}');
```

### Task 3: Query by category-specific attribute

Each query filters on an attribute used by that category rather than relying only on common product columns.

```sql
-- Books with at least 500 pages
SELECT name, (attributes ->> 'pages')::integer AS pages
FROM products
WHERE category = 'book'
  AND (attributes ->> 'pages')::integer >= 500;

-- Laptops with at least 16 GB of RAM
SELECT name, attributes ->> 'cpu' AS cpu
FROM products
WHERE category = 'laptop'
  AND (attributes ->> 'ram_gb')::integer >= 16;

-- Accessories that are wireless
SELECT name, attributes ->> 'color' AS color
FROM products
WHERE category = 'accessory'
  AND attributes @> '{"wireless": true}';
```

### Task 4: Containment query

```sql
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

This returns `Wireless Mouse` for the inserted sample data.

### Task 5: Update JSONB without altering the table

The JSONB concatenation operator `||` adds or replaces top-level keys. `RETURNING` displays the updated row.

```sql
UPDATE products
SET attributes = attributes || '{"discount_pct": 10}'::jsonb
WHERE name = 'Wireless Mouse'
RETURNING name, attributes;
```

Run these plans before creating the index:

`EXPLAIN ANALYZE` executes each query and reports its plan and measured time. Exact output depends on PostgreSQL version, statistics, and data size, so record the output from your own database rather than assuming an index scan. The containment query can use the GIN index on a sufficiently large table, but this five-row example will likely use a sequential scan because that is cheaper. The book and laptop range queries extract and cast JSON text, so this plain GIN index does not directly accelerate those expressions. If those filters become a real workload, consider suitable expression indexes and compare their plans as well.

### Task 7: MongoDB comparison

Run the following in `mongosh` to create the same five documents and query the same category-specific fields.

```javascript
db.products.insertMany([
  { name: "Clean Code", category: "book", price: 499.00,
    attributes: { author: "Robert C. Martin", pages: 464 } },
  { name: "Designing Data-Intensive Applications", category: "book", price: 699.00,
    attributes: { author: "Martin Kleppmann", pages: 616 } },
  { name: "ThinkPad T14", category: "laptop", price: 1299.00,
    attributes: { ram_gb: 32, cpu: "AMD Ryzen 7" } },
  { name: "MacBook Air", category: "laptop", price: 1099.00,
    attributes: { ram_gb: 16, cpu: "Apple M-series" } },
  { name: "Wireless Mouse", category: "accessory", price: 29.99,
    attributes: { color: "black", wireless: true } }
]);

// Task 3 equivalents
db.products.find(
  { category: "book", "attributes.pages": { $gte: 500 } },
  { _id: 0, name: 1, "attributes.pages": 1 }
);

db.products.find(
  { category: "laptop", "attributes.ram_gb": { $gte: 16 } },
  { _id: 0, name: 1, "attributes.cpu": 1 }
);

db.products.find(
  { category: "accessory", "attributes.wireless": true },
  { _id: 0, name: 1, "attributes.color": 1 }
);

// Task 4 containment equivalent
db.products.find(
  { "attributes.wireless": true },
  { _id: 0, name: 1 }
);

// Indexes for the three category-specific queries
db.products.createIndex({ category: 1, "attributes.pages": 1 });
db.products.createIndex({ category: 1, "attributes.ram_gb": 1 });
db.products.createIndex({ category: 1, "attributes.wireless": 1 });
```

MongoDB's direct nested-field query is the equivalent of the PostgreSQL containment filter for this sample. MongoDB uses dot notation and comparison operators such as `$gte`; PostgreSQL uses SQL expressions and JSONB operators. PostgreSQL can use one GIN index for several JSONB containment/existence patterns, while MongoDB commonly uses indexes on the nested fields used by its filters. Either database may need a compound index when queries also filter on `category`. PostgreSQL's fixed columns, joins, and multi-row transactions fit relational workflows naturally. MongoDB's document model can feel more direct when the application stores and retrieves variable-shaped documents as units. Performance and ease of use should be judged with representative data and query plans, not this five-document demonstration.
